# سیستم تشخیص چهره با دوربین (Face Detection With Camera)

این پروژه یک سیستم **حضور و غیاب با تشخیص چهره** است. دو برنامه‌ی مستقل دارد:

1. یک برنامه‌ی **دوربین زنده** که تصویر چند دوربین را هم‌زمان نشان می‌دهد، چهره‌ها را تشخیص می‌دهد، آن‌ها را با افراد ثبت‌شده مقایسه می‌کند و اگر کسی را شناخت، ورودش را در دیتابیس ثبت می‌کند.
2. یک **سرور وب** کوچک که یک نفر جدید را در سیستم ثبت‌نام می‌کند (عکس چهره‌اش را می‌گیرد، در Redis و MySQL ذخیره می‌کند و مدل تشخیص چهره را از نو آموزش می‌دهد).

اگر تازه با این پروژه آشنا می‌شوید، اول ویدیوی معرفی را ببینید:

🎬 **ویدیوی معرفی و آموزش استفاده:** <https://www.aparat.com/v/qylg9w8>

## ۱. فایل‌ها و پوشه‌ها

```
face-Detection-With-Camera-main/
└── faceDetectionWithCamera/
    ├── faceDetectionWithCamera.py      ← برنامه‌ی دوربین زنده (حضور و غیاب)
    ├── server.py                       ← سرور Flask برای ثبت‌نام افراد جدید
    └── assets/
        ├── test.txt                    ← فایل خالی (فقط یک artifact از پروژه‌ی قبلی)
        └── face_detection/
            ├── haarcascade_frontalface_default.xml   ← مدل تشخیص چهره (cascade)
            ├── haarcascade_eye.xml                   ← مدل تشخیص چشم
            ├── haarcascade_left_eye.xml              ← مدل تشخیص چشم چپ (فعلاً استفاده نمی‌شود)
            ├── haarcascade_right_eye.xml             ← مدل تشخیص چشم راست (فعلاً استفاده نمی‌شود)
            └── t                                     ← فایل خالی
```

فایل‌های `t` و `test.txt` هیچ محتوایی ندارند و هیچ جای کد از آن‌ها استفاده نمی‌شود؛ صرفاً در پروژه مانده‌اند.

فایل‌های **XML** مدل‌های آماده‌ی اوپن‌سی‌وی هستند. فایل‌های Haar Cascade آموزش‌دیده‌ای هستند که به رایانه یاد می‌دهند الگوی «صورت انسان» و «چشم» چه شکلی است. خودتان به آن‌ها دست نمی‌زنید و فقط بارگذاری می‌شوند.

> **مهم:** علاوه بر این فایل‌ها، پروژه هنگام اجرا چند فایل و پوشه‌ی دیگر هم می‌سازد که در گیت‌هاب نیست:
>
> - `trainer/model.xml` ← مدل آموزش‌دیده‌ی چهره‌های ثبت‌شده
> - `labels_to_name.json` ← نگاشت شماره‌ی برچسب به نام افراد
>
> این دو فایل را همیشه **server.py** می‌سازد؛ دستی درستشان نکنید.

## ۴. ساخت دیتابیس MySQL

برنامه با یک دیتابیس به نام `face_recognition` و سه جدول کار می‌کند. یک‌بار در MySQL این را اجرا کنید:

```sql
CREATE DATABASE IF NOT EXISTS face_recognition CHARACTER SET utf8mb4 COLLATE utf8mb4_persian_ci;
USE face_recognition;

-- مشخصات افرادی که ثبت‌نام شده‌اند
CREATE TABLE IF NOT EXISTS NewPerson (
    national_code VARCHAR(20) PRIMARY KEY,
    first_name    VARCHAR(100) NOT NULL,
    last_name     VARCHAR(100) NOT NULL,
    image         LONGBLOB              -- عکس چهره (بایت‌های فایل JPG)
);

-- تاریخچه‌ی کامل ورود و خروج‌ها
CREATE TABLE IF NOT EXISTS attendance (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    national_code VARCHAR(20)  NOT NULL,
    checkin_time  VARCHAR(30)  NOT NULL,   -- تاریخ شمسی به شکل رشته: '1403-08-27 14:35:02'
    location      VARCHAR(100) NOT NULL    -- نام دوربینی که فرد دیده شده
);

-- فقط آخرین حضور هر نفر (یک رکورد برای هر کد ملی)
CREATE TABLE IF NOT EXISTS latest_attendance (
    national_code VARCHAR(20) PRIMARY KEY,  -- PRIMARY KEY برای ON DUPLICATE KEY UPDATE لازم است
    first_name    VARCHAR(100),
    last_name     VARCHAR(100),
    last_seen     VARCHAR(30),              -- تاریخ شمسی آخرین دیده شدن
    location      VARCHAR(100)
);
```

**چرا این جدول‌ها این‌طور طراحی شده‌اند؟**

- `attendance` تاریخچه‌ی کامل است؛ هر بار که فرد جدیدی دیده شود (یا ۲ ساعت از حضور قبلی‌اش بگذرد، یا دوربین عوض شود) یک ردیف جدید اینجا اضافه می‌شود.
- `latest_attendance` خلاصه است؛ فقط یک ردیف برای هر کد ملی دارد و همیشه آخرین زمان/مکان را نشان می‌دهد. کلید اصلی روی `national_code` گذاشته شده تا کد بتواند از `ON DUPLICATE KEY UPDATE` استفاده کند و به‌جای ردیف تکراری، همان ردیف را به‌روز کند.
- زمان‌ها به شکل **رشته** ذخیره می‌شوند، نه نوع `DATETIME`، چون کد مستقیم خروجی `JalaliDateTime` را می‌فرستد. (`VARCHAR(30)` هم کافی است.) اگر می‌خواهید در MySQL با تاریخ کار کنید، بعداً می‌توانید ستون را عوض کنید — فقط بدانید کد انتظار رشته دارد.

اگر دیتابیس/رمز شما فرق دارد، دو محل زیر باید هم‌خوان شوند (بخش ۶):
- `faceDetectionWithCamera.py` خط ۳۷ تا ۴۲
- `server.py` خط ۲۲ تا ۲۷

## ۵. راه‌اندازی Redis

Redis یک دیتابیس فوق‌سریع در حافظه است. سرور ثبت‌نام عکس چهره‌ی هر نفر را با کلید «کد ملی» اینجا می‌گذارد و بعد از همین داده‌ها مدل را آموزش می‌دهد.

**ویندوز:** اگر Redis نصب نیست، نسخه‌ی ویندوزی (مثلاً از tporadowski/redis یا Memurai) را نصب کنید. پس از نصب باید سرویس روی پورت 6379 گوش بدهد. اگر `redis-server.exe` را دستی اجرا می‌کنید، پنجره‌اش را نبندید.

**لینوکس:**

```
sudo apt install redis-server
sudo systemctl start redis-server
```

**مک:**

```
brew install redis
brew services start redis
```

**بررسی:**

```
redis-cli ping
```

باید `PONG` برگرداند.

> برنامه به دیتابیس شماره ۰ (`db=0`) وصل می‌شود و **همه‌ی کلیدهایش** را اسکن می‌کند (خط ۹۲ `server.py`). پس هر داده‌ی دیگری در همین دیتابیس Redis نگذارید؛ اگر کلیدی غیرعددی داخلش باشد، آموزش مدل با خطا متوقف می‌شود.

## ۶. تنظیمات داخل کدها

### الف) رمز و آدرس دیتابیس

در **هر دو** فایل مقدارهای زیر را با تنظیمات خودتان یکی کنید:

```python
host='localhost',
database='face_recognition',
user='root',
password='1234'
```

### ب) دوربین‌ها (`faceDetectionWithCamera.py` خط ۲۴۱ تا ۲۴۳)

```python
manager.add_camera("دوربین لپتاپ", 0, "دوربین لپتاپ")
manager.add_camera("نماز خونه",
    "rtsp://admin:shn123456789@192.168.1.101:554/cam/realmonitor?channel=1",
    "نمازخونه")
```

سه آرگومان `add_camera`:

| آرگومان | معنی |
|---|---|
| `name` | اسم نمایشی دوربین (فعلاً فقط در لاگ دیده می‌شود) |
| `source` | منبع تصویر |
| `location` | اسم مکانی که هنگام ثبت حضور در ستون `location` ذخیره می‌شود |

`source` می‌تواند این‌ها باشد:

- `0` (عدد صحیح) → دوربین اول لپ‌تاپ/وبکم. `1` = دوربین دوم، `2` = سوم و...
- رشته‌ی RTSP → دوربین مداربسته‌ی شبکه‌ای.
- رشته‌ی مسیر فایل ویدیو → به‌جای دوربین زنده، از یک فایل پخش می‌کند (برای تست خوب است).

فرم کلی RTSP برای دوربین‌های **Dahua** (همان آدرسی که در کد هست):

```
rtsp://USER:PASSWORD@IP:554/cam/realmonitor?channel=1&subtype=0
```

برای دوربین‌های **Hikvision**:

```
rtsp://USER:PASSWORD@IP:554/Streaming/Channels/101
```

`channel` و `subtype` شماره‌ی کانال و جریان (۰ = کیفیت بالا، ۱ = جریان سبک‌تر) را مشخص می‌کنند; اگر دوربینتان کانال دیگری دارد، تغییرش دهید.

> اگر فقط وبکم لپ‌تاپ دارید، خط `add_camera` مربوط به RTSP را حذف یا کامنت کنید. اگر دوربین در دسترس نباشد، برنامه متوقف نمی‌شود؛ فقط در لاگ خطا می‌دهد و آن خانه‌ی گرید سیاه می‌ماند.

### ج) نام پنجره و چیدمان گرید

- `self.grid_size = (2, 2)` → یعنی حداکثر ۲ ردیف و ۲ ستون؛ **پس حداکثر ۴ دوربین روی صفحه دیده می‌شوند** حتی اگر بیشتر اضافه کنید. برای ۹ دوربین آن را به `(3, 3)` تغییر دهید.
- `self.window_name` → عنوان پنجره.
- `zoom_factor=1.5` → میزان زوم دیجیتالی که روی تصویر دوربین‌های شبکه‌ای اعمال می‌شود (خط ۱۸۵ و پیش‌فرض تابع خط ۷۲). عدد بزرگ‌تر = زوم بیشتر روی مرکز تصویر.

### د) آستانه‌های تشخیص

| مقدار | کجا | معنی |
|---|---|---|
| `scaleFactor=1.3` | `detectMultiScale` در هر دو فایل | تصویر پله‌پله ۳۰٪ کوچک می‌شود تا صورت‌های دورتر هم پیدا شوند. عدد کمتر = دقیق‌تر ولی کندتر |
| `minNeighbors=5` | همان‌جا | حداقل تعداد همسایه‌هایی که باید تأیید کنند تا یک ناحیه «صورت» حساب شود. عدد بیشتر = سخت‌گیرتر، خطای کمتر |
| `confidence < 100` | خط ۱۰۲ فایل دوربین | **آستانه‌ی شناسایی.** هرچه کمتر باشد سخت‌گیرتر است. مدل LBPH «فاصله» برمی‌گرداند، نه درصد؛ پس عددِ کمتر = شباهت بیشتر |
| `time_diff >= 7200` | خط ۱۲۸ | فاصله‌ی ۲ ساعت (به ثانیه) برای ثبت رکورد جدید در `attendance` |

### ه) پورت سرور

`app.run(debug=True)` یعنی روی پورت پیش‌فرض **5000** و در حالت دیباگ (با ری‌استارت خودکار هنگام تغییر کد). برای استفاده‌ی واقعی `debug=True` را به `False` تغییر دهید و پورت را صریح بدهید:

```python
app.run(host='0.0.0.0', port=5000, debug=False)
```

## ۷. اجرای برنامه‌ی دوربین

پیش‌نیاز: مدل `trainer/model.xml` **باید وجود داشته باشد**. این مدل را سرور می‌سازد. اگر هنوز هیچ کسی ثبت‌نام نشده، فایل مدل نیست و اجرای برنامه با این خطا متوقف می‌شود:

```
cv2.error: ... (trainer/model.xml) can't be opened
```

راه‌حل: اول با سرور حداقل یک نفر را ثبت‌نام کنید (بخش ۹)، یا برای تست این خط را از `__init__` موقتاً حذف کنید (ولی آن‌وقت `predict` خطا می‌دهد — بهتر است واقعاً یک نفر ثبت شود).

### اجرا

```
cd faceDetectionWithCamera
python faceDetectionWithCamera.py
```

### چه می‌بینید

پنجره‌ای با عنوان «Face Recognition System» باز می‌شود:

- **حالت گرید:** فریم همه‌ی دوربین‌ها کنار هم در یک شبکه (پیش‌فرض ۲×۲).
- **حالت تمام‌صفحه:** روی هر تصویر **دوبار کلیک** کنید تا فقط همان دوربین کل پنجره را پر کند؛ دوباره دوبار کلیک کنید تا به گرید برگردید.
- دور صورت‌هایی که تشخیص داده شود یک **مستطیل سبز** کشیده می‌شود.
- اگر چهره با یک نفر ثبت‌شده تطبیق پیدا کند (فاصله < 100)، رکورد حضورش در دیتابیس ثبت می‌شود و در ترمینال/لاگ یک خط اطلاعاتی چاپ می‌شود:

## ۹. ثبت‌نام یک نفر جدید (فرستادن عکس به سرور)

سرور فقط یک مسیر دارد:

```
POST http://localhost:5000/upload
Content-Type: application/json
```

بدنه‌ی JSON:

```json
{
  "image": "data:image/jpeg;base64,/9j/4AAQSkZJRg...",
  "nationalCode": "0012345678",
  "firstName": "علی",
  "lastName": "رضایی"
}
```

| فیلد | الزامی | توضیح |
|---|---|---|
| `image` | ✅ | عکس چهره به Base64. کد انتظار دارد رشته با کاما از هم جدا شده باشد و بخش دوم را می‌خواند (`split(',')[1]`)، یعنی شکل `data:image/jpeg;base64,...` لازم است |
| `nationalCode` | ✅ | کد ملی، همان چیزی که در `trainer` به‌عنوان برچسب (label) استفاده می‌شود |
| `firstName` | ✅ | نام |
| `lastName` | ✅ | نام خانوادگی |

### مثال: با پایتون (ساده‌ترین راه)

یک فایل مثلاً `register.py` بسازید (کنار پوشه‌ی پروژه، نه داخل آن) و این را داخلش بگذارید:

```python
import base64, json, urllib.request

with open("ali.jpg", "rb") as f:
    b64 = base64.b64encode(f.read()).decode()

payload = {
    "image": "data:image/jpeg;base64," + b64,
    "nationalCode": "0012345678",
    "firstName": "علی",
    "lastName": "رضایی",
}
req = urllib.request.Request(
    "http://localhost:5000/upload",
    data=json.dumps(payload).encode(),
    headers={"Content-Type": "application/json"},
    method="POST",
)
print(urllib.request.urlopen(req).read().decode())
```

اجرا: `python register.py`

### مثال: با curl (لینوکس/مک)

```
IMG=$(base64 -w0 ali.jpg)
curl -X POST http://localhost:5000/upload \
  -H "Content-Type: application/json" \
  -d "{\"image\":\"data:image/jpeg;base64,$IMG\",\"nationalCode\":\"0012345678\",\"firstName\":\"علی\",\"lastName\":\"رضایی\"}"
```

### پاسخ‌های سرور

| وضعیت | پاسخ | معنی |
|---|---|---|
| 200 | `{"status":"success","message":"اطلاعات با موفقیت ذخیره شد و مدل به‌روزرسانی گردید."}` | ثبت‌نام انجام شد و مدل دوباره آموزش دید |
| 400 | `{"status":"error","message":"فیلد ... الزامی است."}` | یکی از فیلدها خالی است |
| 400 | `{"status":"error","message":"چهره شناسایی نشد یا چهره ناقص است"}` | در عکس صورت پیدا نشد، یا **کمتر از ۲ چشم** در ناحیه‌ی صورت تشخیص داده شد |
| 400 | `{"status":"error","message":"تصویر معتبر نیست."}` | Base64 خراب است یا عکس قابل باز شدن نیست |
| 500 | `{"status":"error","message":"خطا در پردازش تصویر"}` | خطای داخلی (مثلاً Redis قطع است) |

### نکات مهم برای عکس خوب

- عکس **فقط یک نفر** باشد؛ سرور فقط اولین صورتِ پیدا‌شده را بررسی می‌کند.
- صورت **روبه‌دوربین، نور کافی، بدون عینک آفتابی و ماسک**.
- هر دو چشم دیده شوند، وگرنه سرور عکس را رد می‌کند (`len(eyes_detected) < 2` در خط ۷۲).
- برای هر کد ملی **فقط یک عکس** نگه داشته می‌شود؛ اگر همان کد ملی را دوباره بفرستید، عکس قبلی در Redis با عکس جدید جایگزین می‌شود (کلید Redis همان کد ملی است) ولی در جدول `NewPerson` رکورد قبلی دست نمی‌خورد.

## ۱۰. پروژه از داخل چطور کار می‌کند

### تصویر بزرگ

```
 ┌─────────────────────────┐        ┌───────────────────────────┐
 │  مرورگر / اپ موبایل     │ ─────▶ │  server.py  (Flask :5000) │
 │  عکس + کد ملی + نام     │  POST  │  /upload                  │
 └─────────────────────────┘        └───────────┬───────────────┘
                                                │
                      ┌─────────────────────────┼─────────────────────┐
                      ▼                         ▼                     ▼
             ┌────────────────┐       ┌──────────────────┐   ┌──────────────────┐
             │ Redis          │       │ MySQL            │   │ trainer/model.xml│
             │ key=کد ملی     │       │ NewPerson        │   │ + labels_to_name │
             │ value=عکس+نام  │       │ (مشخصات+عکس)     │   │ (مدل آموزش‌دیده) │
             └───────┬────────┘       └──────────────────┘   └────────┬─────────┘
                     │  همه‌ی کلیدها را می‌خواند و مدل را آموزش می‌دهد │
                     └──────────────────────────────────────────────┘
                                                │
                                                ▼ (مدل فقط هنگام شروع خوانده می‌شود)
 ┌──────────────────┐        ┌─────────────────────────────────────────┐
 │ دوربین وبکم (0)  │ ─────▶ │ faceDetectionWithCamera.py              │
 │ دوربین RTSP      │  فریم  │ 1) تشخیص صورت با Haar Cascade            │
 └──────────────────┘        │ 2) شناسایی با LBPH                      │
                             │ 3) ثبت در attendance / latest_attendance │
                             └─────────────────────────────────────────┘
```

### مرحله ۱ — تشخیص صورت (Face Detection) چیست؟

«تشخیص» یعنی پیدا کردن **محل** صورت در تصویر. اینجا با روش Haar Cascade انجام می‌شود که در فایل‌های XML داخل `assets` است. این روش کل تصویر را (در اندازه‌های مختلف) اسکن می‌کند و می‌گوید «اینجا یک مستطیل شبیه صورت هست». نتیجه‌اش چیزی مثل `(x, y, w, h)` است: مختصات گوشه‌ی بالا-چپ و عرض و ارتفاع مستطیل.

مهم: Haar Cascade **نمی‌گوید این صورت چه کسی است**؛ فقط می‌گوید «اینجا صورت است».

### مرحله ۲ — شناسایی (Recognition) چیست؟

«شناسایی» یعنی گفتن **این صورت متعلق به کیست**. اینجا با الگوریتم **LBPH** (Local Binary Patterns Histograms) انجام می‌شود که در `cv2.face` هست. این الگوریتم هر صورت را به یک «امضای عددی» تبدیل می‌کند و با امضاهای ذخیره‌شده مقایسه می‌کند؛ نزدیک‌ترین را برمی‌گرداند.

مدل LBPH در فایل `trainer/model.xml` ذخیره می‌شود. هر «برچسب» (label) در این مدل یک عدد است — و این پروژه از **کد ملی عددی** به‌عنوان برچسب استفاده می‌کند. به همین دلیل، وقتی `predict` جواب می‌دهد، آن عدد مستقیماً کد ملی است و کد می‌تواند با آن نام فرد را از `NewPerson` بخواند.

### مرحله ۳ — یعنی چه `confidence`؟

`predict` دو چیز برمی‌گرداند: `label` (کد ملی) و `confidence`. دقت کنید که در LBPH، `confidence` در واقع **فاصله** است، نه درصد صحت؛ **هرچه کوچک‌تر، شبیه‌تر**. مقدار صفر یعنی تطابق کامل. کد فقط وقتی فرد را می‌پذیرد که این فاصله از **۱۰۰** کمتر باشد (خط ۱۰۲). هرچه عکس ثبت‌نام با شرایط دوربین (نور، فاصله، زاویه) نزدیک‌تر باشد، این عدد کوچک‌تر می‌شود.

### مرحله ۴ — پیش‌پردازش تصویر

قبل از تشخیص، دو کار روی فریم انجام می‌شود (خط ۹۴ و ۹۵):

1. **تبدیل به خاکستری**: `cvtColor(..., COLOR_BGR2GRAY)` — چون تشخیص روی رنگ کار نمی‌کند و خاکستری هم سریع‌تر است.
2. **یکسان‌سازی هیستوگرام**: `equalizeHist` — کنتراست تصویر را یکنواخت می‌کند تا در نور کم/زیاد هم صورت قابل تشخیص باشد.

### مرحله ۵ — قاعده‌ی ثبت حضور (مهم‌ترین بخش منطقی)

فرض کنید علی الان جلوی دوربین است و ۳۰ فریم پشت سر هم شناسایی می‌شود. اگر هر فریم یک رکورد بزند، دیتابیس پر از رکورد تکراری می‌شود. برای همین `last_checkin` (یک دیکشنری در حافظه که برای هر کد ملی، زمان و مکان آخرین ثبت را نگه می‌دارد) استفاده می‌شود:

- اگر فرد **قبلاً ثبت نشده** → رکورد جدید در `attendance` بزن.
- اگر **قبلاً ثبت شده**:
  - اگر `>= 7200` ثانیه (۲ ساعت) از ثبت قبلی گذشته باشد → رکورد جدید بزن.
  - یا اگر **دوربین (لوکیشن) عوض شده باشد** → رکورد جدید بزن.
  - وگرنه → هیچ چیز در `attendance` اضافه نکن.
- در **هر صورت** (چه رکورد جدید، چه نه) ردیف `latest_attendance` را به‌روز کن تا «آخرین حضور» همیشه تازه بماند.

و یک نکته‌ی زمان‌بندی: در `main` این خط هست:

```python
schedule.every(2).hours.do(manager.last_checkin.clear)
```

یعنی هر ۲ ساعت حافظه‌ی `last_checkin` پاک می‌شود. نتیجه: اگر فردی ۲ ساعت مداوم جلوی دوربین بماند، در عمل هر ۲ ساعت یک‌بار دوباره رکورد می‌گیرد — حتی اگر قانون ۲ ساعته هم خودش همان لحظه فاصله را چک کند. دو مکانیزم همدیگر را تقویت می‌کنند و فقط برای اطمینان بیشترند.

زمان‌هایی که در دیتابیس ذخیره می‌شوند **شمسی** هستند (`JalaliDateTime.now()`)، به شکل رشته مثل `1403-08-27 14:35:02`. زمان پردازش داخلی (`datetime.now()`) میلادی است و فقط برای محاسبه‌ی فاصله‌ی ۲ ساعت استفاده می‌شود؛ هیچ‌جا ذخیره نمی‌شود.

### مرحله ۶ — زوم دیجیتال برای دوربین‌های شبکه‌ای

دوربین‌های مداربسته معمولاً خیلی از صورت فاصله دارند. کد برای دوربین‌هایی که منبعشان عدد صفر (وبکم) نیست، این کار را می‌کند (`adjust_focal_distance`):

1. وسط تصویر را برش می‌زند (با `zoom_factor=1.5` یعنی ۶۶٪ عرض و ارتفاع وسط).
2. برش را به ۶۴۰×۴۸۰ بزرگ می‌کند.

نتیجه: تصویر «زوم‌شده» می‌شود، صورت‌ها بزرگ‌تر و قابل تشخیص‌تر می‌شوند. ولی حاشیه‌های تصویر از دست می‌روند — اگر دوربین را طوری بگذارید که صورت در گوشه باشد، ممکن است کامل حذف شود.

### مرحله ۷ — نمایش گرید و تمام‌صفحه

`show_interface` فریم‌های هر دوربین را با `np.hstack` کنار هم و با `np.vstack` زیر هم می‌چیند. برای اینکه بین تصاویر فاصله باشد، در محاسبه‌ی خانه‌ی کلیک، هر خانه ۶۴۰+۱۰ پیکسل عرض و ۴۸۰+۱۰ پیکسل ارتفاع فرض شده است:

```python
col = x // (640 + 10)
row = y // (480 + 10)
```

> این یعنی تصویر نهایی گرید واقعاً ۱۰ پیکسل فاصله‌ی سیاه بین خانه‌ها **ندارد** (چون فقط کنار هم چسبانده شده‌اند)، ولی محاسبه‌ی کلیک آن فاصله را فرض می‌کند. تا ۴ دوربین پیش‌فرض تفاوتش خیلی محسوس نیست؛ اگر با کلیک دوبار مشکل داشتید، جای درست کلیک کمی جابه‌جا شود، همین است.

اگر هیچ دوربینی متصل نشود، `np.zeros((480, 640, 3))` یک **تصویر کاملاً سیاه** می‌سازد و نمایش می‌دهد تا پنجره باز بماند.

### مرحله ۸ — آموزش مدل در سرور

`train_model()` هر بار که یک نفر آپلود می‌کند، **همه‌ی** کلیدهای Redis را می‌خواند، عکس Base64 هر کدام را به تصویر خاکستری ۱۰۰×۱۰۰ تبدیل می‌کند، برچسبش را `int(key)` می‌گذارد و از صفر مدل LBPH را آموزش می‌دهد؛ بعد فایل `trainer/model.xml` و `labels_to_name.json` را می‌نویسد.

نکته: آموزش **افزایشی** نیست؛ هر بار کل دیتاست از نو آموزش می‌بیند. برای چند صد نفر این چند ثانیه/دقیقه بیشتر طول نمی‌کشد (LBPH سریع است)، ولی با هزاران نفر کند می‌شود.

## ۱۱. توضیح خط به خط فایل `faceDetectionWithCamera.py`

این فایل ۲۸۰ خط است و یک کلاس `CameraManager` و تابع `main` دارد.

### خط ۱ تا ۱۶ — import و لاگ

```python
import cv2, numpy as np, mysql.connector
from datetime import datetime

```

- `logging.basicConfig(level=logging.INFO)` → همه‌ی پیام‌ها با زمان چاپ می‌شوند. اگر می‌خواهید پیام‌های ریزتر (DEBUG) هم ببینید، `INFO` را به `DEBUG` تغییر دهید.
- `logging.getLogger(__name__)` یک لاگر برای همین فایل می‌سازد.

### خط ۱۹ تا ۲۶ — آغاز کلاس

`CameraManager` همه‌ی وضعیت برنامه را در خود نگه می‌دارد:

| متغیر | معنی |
|---|---|
| `self.cameras` | لیست دیکشنری‌های دوربین‌ها |
| `self.grid_size = (2, 2)` | چیدمان گرید: ۲ ردیف، ۲ ستون |
| `self.active_cam = -1` | کدام دوربین تمام‌صفحه است؛ `-1` یعنی حالت گرید |

### خط ۲۸ تا ۳۳ — بارگذاری مدل‌ها

```python
self.face_cascade = cv2.CascadeClassifier(
    cv2.data.haarcascades + 'haarcascade_frontalface_default.xml')
self.face_recognizer = cv2.face.LBPHFaceRecognizer_create()
self.face_recognizer.read('trainer/model.xml')
```

- `cv2.data.haarcascades` پوشه‌ی مدل‌های همراه خود اوپن‌سی‌وی است؛ یعنی **این فایل از XMLهای داخل `assets` استفاده نمی‌کند** و به نسخه‌ی نصب‌شده‌ی OpenCV اتکا دارد. (سرور برعکس، از `assets` استفاده می‌کند.)
- `LBPHFaceRecognizer_create()` شیئی از الگوریتم شناسایی می‌سازد.
- `read('trainer/model.xml')` مدل آموزش‌دیده را از دیسک بارگذاری می‌کند. اگر فایل نباشد، **همین‌جا برنامه با خطا می‌میرد** — این همان دلیلی است که باید قبل از اولین اجرا یک نفر را ثبت‌نام کنید.

### خط ۳۵ تا ۴۶ — اتصال دیتابیس

اتصال داخل `try/except` است؛ اگر MySQL بالا نباشد، برنامه متوقف نمی‌شود، فقط `self.db = None` می‌شود و هر بار که بخواهد حضور ثبت کند، لاگ خطا می‌دهد. (در سرور برعکس است — آنجا اتصال بدون `try` است و اگر MySQL نباشد سرور کامل بالا نمی‌آید.)

### خط ۴۸ تا ۴۹ — حافظه‌ی آخرین ثبت

`self.last_checkin = {}` — دیکشنری `{کد_ملی: (زمان, لوکیشن)}`. فقط در حافظه است و با بسته شدن برنامه پاک می‌شود.

### خط ۵۱ تا ۷۰ — `add_camera(name, source, location)`

- `cv2.VideoCapture(source)` دوربین یا فایل را باز می‌کند.
- `cap.isOpened()` بررسی می‌کند آیا باز شد.
- `is_external`: اگر منبع `0` (عدد) بود، وبکم است (`False`)؛ هر چیز دیگری «خارجی» حساب می‌شود (`True`) و زوم دیجیتال می‌گیرد.

  > اگر دوربین لپ‌تاپ شما روی ایندکس `1` باشد، این کد آن را هم «خارجی» می‌بیند و رویش زوم می‌کند. برای جلوگیری، شرط خط ۵۹ را به `source in (0, 1)` تغییر دهید.
- هر دوربین در `self.cameras` با کلیدهای `cap`, `name`, `location`, `frame`, `is_external` ثبت می‌شود.
- اگر باز نشد، `cap.release()` و لاگ خطا.

### خط ۷۲ تا ۸۴ — `adjust_focal_distance(frame, zoom_factor=1.5)`

همان زوم دیجیتال توضیح‌داده‌شده. `x1` و `y1` محاسبه می‌کنند برش از کجا شروع شود تا وسط تصویر باشد. خروجی همیشه ۶۴۰×۴۸۰ است. اسمش «تنظیم فاصله‌ی کانونی» است ولی در واقع لنز تغییر نمی‌کند؛ فقط تصویر میانی بریده و بزرگ می‌شود.

### خط ۸۶ تا ۱۰۵ — `process_faces(frame, location)`

گام‌به‌گام برای هر فریم:

1. خاکستری‌کردن + `equalizeHist`.
2. `detectMultiScale` → لیست مستطیل صورت‌ها.
3. برای هر صورت:
   - مستطیل سبز (`(0,255,0)`, ضخامت ۲) روی فریم رنگی می‌کشد.
   - ناحیه‌ی صورت را از تصویر خاکستری می‌برد (`face_roi`).
   - `predict(face_roi)` → `(label, confidence)`.
   - اگر `confidence < 100` → `log_attendance(str(label), location)`.
4. کل فریم را ۶۴۰×۴۸۰ ریسایز و برمی‌گرداند.

> **دو نکته‌ی ریز:** (۱) `face_roi` به اندازه‌ی مدل آموزش (۱۰۰×۱۰۰) ریسایز **نمی‌شود**؛ LBPH نسبت به اندازه تا حدی مقاوم است ولی بهتر است برای دقت بیشتر `cv2.resize(face_roi, (100,100))` اضافه شود. (۲) مستطیل روی `frame` رنگی کشیده می‌شود، ولی مقایسه روی نسخه‌ی خاکستری انجام می‌شود — این کاملاً درست است و لازم.

### خط ۱۰۷ تا ۱۷۱ — `log_attendance(national_code, location)`

این تابع منطق بخش ۱۰/مرحله ۵ را پیاده می‌کند:

1. اگر دیتابیس وصل نیست → لاگ خطا و خروج.
2. زمان میلادی (`now`) و زمان شمسی رشته‌ای (`jalali_time`) را می‌گیرد.
3. با نگاه به `last_checkin` تصمیم می‌گیرد رکورد جدید در `attendance` بزند یا نه (فاصله ≥ ۲ ساعت یا لوکیشن متفاوت).
4. اگر باید بزند: `INSERT INTO attendance (national_code, checkin_time, location)`.
5. از `NewPerson` نام و نام‌خانوادگی را می‌خواند؛ اگر نبود «نامشخص».
6. `INSERT ... ON DUPLICATE KEY UPDATE` در `latest_attendance` — یک ردیف برای هر نفر که همیشه به‌روز است.
7. `self.last_checkin[national_code] = (now, location)` را به‌روز می‌کند.

> `cursor` در این تابع `close` نمی‌شود. برای یک برنامه‌ی کوچک مشکل جدی نمی‌سازد (با هر فریم یک cursor جدید ساخته می‌شود و پایتون زباله‌روبیش می‌کند)، ولی اگر برنامه روزها بدون ری‌استارت بماند و MySQL هشدار «too many connections» داد، باید `finally: cursor.close()` اضافه شود.

### خط ۱۷۳ تا ۱۸۸ — `update_frames()`

برای هر دوربین یک فریم می‌خواند:

- اگر فریم آمد: در صورت خارجی بودن، زوم دیجیتال؛ بعد `process_faces` و ذخیره در `cam['frame']`.
- اگر نیامد: فریم سیاه جایگزین می‌کند تا برنامه کرش نکند.

### خط ۱۹۰ تا ۲۰۸ — `toggle_fullscreen(x, y)`

دوبار کلیک با فاصله‌ی کمتر از ۵۰۰ میلی‌ثانیه **نادیده** گرفته می‌شود (جلوگیری از فعال‌شدن چندباره). بعد:

- اگر در حالت گرید بود: با مختصات کلیک، ردیف و ستون را حساب می‌کند و اگر آن خانه دوربین دارد، `active_cam` را روی آن می‌گذارد.
- اگر در حالت تمام‌صفحه بود: برگرد به گرید (`-1`).

### خط ۲۱۰ تا ۲۳۴ — `show_interface()`

- حالت تمام‌صفحه: فقط فریم دوربین فعال.
- حالت گرید: فریم‌ها ردیف‌به‌ردیف `hstack` و بعد `vstack` می‌شوند؛ خانه‌های خالی با فریم سیاه پر می‌شوند تا شکل شبکه حفظ شود.
- بدون دوربین: یک فریم سیاه.

### خط ۲۳۸ تا ۲۷۵ — `main()`

1. `manager = CameraManager()`.
2. دو دوربین اضافه می‌شود (خط ۲۴۲ و ۲۴۳).
3. `schedule.every(2).hours.do(manager.last_checkin.clear)`.
4. تابع `mouse_handler` فقط دوبار کلیک چپ را به `toggle_fullscreen` می‌دهد.
5. پنجره‌ی قابل تغییر اندازه ساخته و یک فریم سیاه نمایش داده می‌شود (تا پنجره پیش از ورود به حلقه وجود داشته باشد).
6. `cv2.setMouseCallback` داخل `try` است تا در محیطی که ماوس ندارد، برنامه نمیرد.
7. حلقه‌ی بی‌نهایت: `update_frames` → `show_interface` → `schedule.run_pending` → اگر کلید Esc زده شد خارج شو.
8. `finally`: آزاد کردن همه‌ی دوربین‌ها، بستن پنجره‌ها، بستن دیتابیس.

> **چرا `schedule.run_pending()` لازم است؟** کتابخانه‌ی `schedule` خودش کارها را اجرا نمی‌کند؛ فقط وقتی `run_pending` صدا زده شود چک می‌کند آیا زمان اجرای کاری رسیده یا نه. اگر آن را از حلقه بردارید، پاک‌سازی هر ۲ ساعت هرگز اجرا نمی‌شود.

## ۱۲. توضیح خط به خط فایل `server.py`

این فایل ۲۱۴ خط است.

### خط ۱ تا ۱۵ — import، ساخت پوشه‌ی trainer، لاگ

`os.makedirs("trainer", exist_ok=True)` یعنی پوشه‌ی `trainer` را در پوشه‌ی جاری بساز (اگر نبود). چون `model.xml` باید همان‌جا نوشته شود، این خط از اول اطمینان می‌دهد پوشه هست.

### خط ۱۷ تا ۲۷ — اتصال Redis و MySQL

- `redis.StrictRedis(host='localhost', port=6379, db=0, decode_responses=True)` — `decode_responses=True` باعث می‌شود خروجی `get` به‌جای `bytes` رشته باشد و مستقیم با `json.loads` کار کند.
- اتصال MySQL **بدون `try`** است: اگر MySQL بالا نباشد یا رمز اشتباه باشد، سرور همین‌جا کرش می‌کند. اگر می‌خواهید پیام واضح‌تری ببینید، این را هم داخل `try/except` بگذارید.

### خط ۳۰ تا ۳۱ — Flask و CORS

`Flask(__name__)` اپ را می‌سازد؛ `CORS(app)` اجازه می‌دهد مرورگرها از دامنه‌ی دیگر (یا اپ موبایل) به این سرور درخواست بزنند. بدون `CORS`، صفحه‌وبی که روی `localhost:3000` اجراست نمی‌تواند به `localhost:5000` درخواست بدهد.

### خط ۳۴ تا ۴۳ — مدل‌های Haar

```python
HAAR_CASCADE_PATHS = {
    "face": "assets/face_detection/haarcascade_frontalface_default.xml",
    "eye":  "assets/face_detection/haarcascade_eye.xml",
}
```

اگر این دو فایل نباشند `raise FileNotFoundError` می‌کند. برخلاف فایل دوربین، اینجا از **XMLهای داخل پروژه** استفاده می‌شود. (پس اگر پروژه را از جای اشتباه اجرا کنید، همین‌جا خطا می‌گیرید — یادآوری بخش ۳.)

`eye_cascade` قبلاً آموزش ندیده، فقط بارگذاری شده است؛ در `detectMultiScale` استفاده می‌شود و پیش‌فرض‌هایش کافی است.

### خط ۴۶ تا ۵۵ — `base64_to_cv2_image`

شکل ورودی `data:image/jpeg;base64,XXXX` است. `split(',')[1]` پیشوند را دور می‌ریزد و فقط `XXXX` را می‌گیرد. `base64.b64decode` رشته را به بایت، `np.frombuffer` به آرایه‌ی numpy و `cv2.imdecode` به تصویر OpenCV تبدیل می‌کند. اگر عکس خراب باشد `ValueError("تصویر معتبر نیست.")` می‌دهد.

### خط ۵۷ تا ۸۱ — `detect_and_validate_face`

1. خاکستری می‌کند.
2. صورت‌ها را پیدا می‌کند؛ اگر صفر باشد `(None, None)`.
3. **اولین** صورت را جدا می‌کند، به ۲۰۰×۲۰۰ ریسایز می‌کند و داخلش دنبال چشم می‌گردد.
4. اگر کمتر از ۲ چشم بود → `None` (عکس رد می‌شود).
5. اگر خوب بود → `(face, (x, y, w, h))`.

> `return` داخل حلقه است؛ یعنی اگر عکس چند صورت داشته باشد، فقط اولی بررسی می‌شود و بقیه نادیده گرفته می‌شوند.

### خط ۸۳ تا ۱۲۰ — `train_model()`

1. `scan_iter()` روی همه‌ی کلیدهای Redis می‌گردد.
2. برای هر کلید: JSON را به دیکشنری، `faceImage` را به تصویر **خاکستری**، و ریسایز به ۱۰۰×۱۰۰.
3. `labels.append(int(key))` — کد ملی به عدد.
4. `labels_to_name[int(key)] = {"full_name": "نام فامیلی", "student_id": key}`.
5. اگر داده هست: `LBPHFaceRecognizer_create()`، `.train(faces, labels)`، `.write("trainer/model.xml")`، و ذخیره‌ی `labels_to_name.json`.
6. اگر داده نیست: لاگ هشدار و هیچ فایلی نوشته نمی‌شود.

> `labels_to_name.json` نوشته می‌شود ولی **هیچ‌جای کد خوانده نمی‌شود**؛ برنامه‌ی دوربین نام را از جدول `NewPerson` می‌خواند. این فایل برای استفاده‌ی احتمالی بعدی/خارج از این پروژه نگه داشته شده است.

### خط ۱۲۲ تا ۱۳۸ — `save_to_redis`

عکس را JPG می‌کند، Base64 می‌کند و همراه نام و زمان شمسی در JSON می‌گذارد:

```json
{
  "firstName": "علی",
  "lastName": "رضایی",
  "faceImage": "/9j/4AAQ...",
  "detectionTime": "1403-08-27 14:35:02"
}
```

کلید Redis = کد ملی. پس برای هر نفر فقط یک رکورد (آخرین عکس) نگه داشته می‌شود.

### خط ۱۴۰ تا ۱۶۸ — `save_to_mysql`

- `SELECT COUNT(*) FROM NewPerson WHERE national_code = %s`.
- اگر صفر بود: عکس را JPG کرده، به بایت تبدیل می‌کند و با `INSERT` در ستون `image` (LONGBLOB) می‌گذارد.
- اگر بود: فقط لاگ می‌کند و **عکس/نام جدید را جایگزین نمی‌کند**.

> نکته: در این بلوک جاهایی عکس از تصویر رنگی/خاکستری JPG می‌شود و در Redis همان تصویر خاکستری ۲۰۰×۲۰۰ ذخیره شده است. عکس داخل MySQL همان چیزی است که در پاسخ سرور آمده؛ تفاوت جزئی در پروژه وجود دارد و رفتار برنامه‌ی دوربین به آن وابسته نیست (دوربین از Redis/مدل استفاده می‌کند، نام را از MySQL می‌خواند).

### خط ۱۷۰ تا ۱۷۶ — `validate_inputs`

چهار فیلد `image`, `nationalCode`, `firstName`, `lastName` را چک می‌کند. فیلد خالی یا `null` → `ValueError` با پیام فارسی.

### خط ۱۷۹ تا ۱۹۱ — روت `/upload`

ترتیب کار:

1. `request.json` خواندن بدنه.
2. اعتبارسنجی فیلدها.
3. `base64_to_cv2_image`.
4. `detect_and_validate_face` — اگر رد شد، ۴۰۰.
5. `save_to_redis`.
6. `save_to_mysql`.
7. `train_model()` — مدل کامل بازآموزی.
8. پاسخ ۲۰۰ موفقیت.

> اگر وسط این مراحل خطا رخ دهد و کد به مرحله‌ی ۷ نرسد، ممکن است Redis به‌روز شده باشد ولی مدل آموزش ندیده باشد. در آن صورت وقتی سرور را دوباره اجرا کنید (یا یک ثبت‌نام دیگر انجام دهید) مدل از Redis بازسازی می‌شود.

### خط ۱۹۳ تا ۲۱۱ — مدیریت خطاها

- `ValueError` → ۴۰۰ با پیام خودش (خطاهای اعتبارسنجی و Base64).
- هر خطای دیگر → ۵۰۰ با پیام کلی «خطا در پردازش تصویر». جزئیات فقط در لاگ سرور است.

### خط ۲۱۳ تا ۲۱۴ — اجرای سرور

`app.run(debug=True)` → پورت ۵۰۰۰، حالت دیباگ. در حالت دیباگ Flask از هر IP ای گوش نمی‌دهد (فقط 127.0.0.1)؛ اگر می‌خواهید از دستگاه دیگری در شبکه به سرور دسترسی داشته باشید، `host='0.0.0.0'` را صریح بدهید و `debug=False`.

## ۱۳. نکات مهم، محدودیت‌ها و دام‌ها

این‌ها را قبل از استفاده‌ی واقعی بخوانید؛ همه‌شان از کد استخراج شده‌اند و تعدادی از آن‌ها «محدودیت طراحی فعلی» هستند نه باگ، ولی دانستنشان لازم است:

1. **`trainer/model.xml` باید از قبل وجود داشته باشد** تا برنامه‌ی دوربین اجرا شود. مدل فقط هنگام شروع خوانده می‌شود؛ بعد از هر ثبت‌نام جدید، برنامه‌ی دوربین را ری‌استارت کنید.
2. **حداکثر ۴ دوربین نمایش داده می‌شود** با `grid_size=(2,2)`. دوربین‌های بیشتر اضافه می‌شوند و فریم می‌گیرند ولی در گرید دیده نمی‌شوند.
3. **فقط اولین صورت در عکس ثبت‌نام بررسی می‌شود**؛ عکس با چند نفر، بقیه را نادیده می‌گیرد.
4. **حداقل ۲ چشم لازم است**، وگرنه ثبت‌نام رد می‌شود. برای عکس‌های کوچک کلاه‌دار/عینکی، ممکن است `haarcascade_eye` چشم‌ها را پیدا نکند.
5. **برای هر کد ملی یک عکس.** ثبت مجدد همان کد ملی، عکس Redis را جایگزین می‌کند ولی رکورد MySQL را نه.
6. **کد ملی باید عددی باشد**، چون `int(key)` در آموزش مدل استفاده می‌شود. کلید غیرعددی در Redis باعث خطا می‌شود. کد ملی را با صفرهای ابتدایی به شکل رشته بفرستید (`"0012345678"`)؛ `int` صفرها را حذف می‌کند، پس وقتی مدل برچسب را برمی‌گرداند `"12345678"` است. اگر رکورد `NewPerson` را با `"0012345678"` ذخیره کرده باشید، نام پیدا نمی‌شود و «نامشخص» می‌آید. **پس کد ملی را بدون صفر ابتدایی بفرستید یا همه‌جا یکدست نگه دارید.**
7. **آستانه‌ی ۱۰۰** برای `confidence` سختگیرانه است. اگر افراد شناخته نمی‌شوند، اول عکس ثبت‌نام و شرایط نور را بهتر کنید؛ اگر می‌خواهید حساسیت را تنظیم کنید، این عدد را تغییر دهید (بالاتر = آسان‌گیرتر و خطر اشتباه بیشتر).
8. **زوم دیجیتال ۱.۵ روی همه‌ی منابع غیر صفر** اعمال می‌شود. اگر دوربین لپ‌تاپ شما `1` است، آن هم زوم می‌شود؛ شرط خط ۵۹ را اصلاح کنید.
9. **زمان ذخیره‌شده شمسی و رشته‌ای است**؛ جست‌وجو/مرتب‌سازی بر اساس تاریخ در SQL با رشته انجام می‌شود. برای گزارش‌گیری‌های پیچیده بهتر است بعداً ستون `DATETIME` اضافه کنید.
10. **`schedule` حافظه را هر ۲ ساعت پاک می‌کند**، پس در بدترین حالت ممکن است فرد در یک بازه‌ی ۲ ساعته بیشتر از یک‌بار رکورد بگیرد (اگر هنوز جلوی دوربین باشد).
11. **مسیرها نسبی‌اند** — همیشه از داخل پوشه‌ی `faceDetectionWithCamera` اجرا کنید.
12. **DB و Redis** باید قبل از شروع هر دو برنامه روشن باشند. برنامه‌ی دوربین بدون DB هم اجرا می‌شود ولی چیزی ثبت نمی‌کند؛ سرور بدون DB/Redis اصلاً بالا نمی‌آید.
13. **پورت ۵۰۰۰** ممکن است روی مک با AirPlay اشغال باشد؛ در این صورت پورت دیگری بدهید.
14. **حالت دیباگ Flask** برای تست خوب است ولی برای استفاده‌ی واقعی خاموشش کنید (امنیت + اجرا نشدن دو نسخه‌ی موازی).
15. فایل‌های **`t` و `test.txt`** خالی‌اند و استفاده نمی‌شوند؛ فقط می‌توانند حذف شوند.

## ۱۴. عیب‌یابی مشکلات رایج

| مشکل | علت احتمالی | راه‌حل |
|---|---|---|
| `ModuleNotFoundError: No module named 'cv2'` | OpenCV نصب نیست یا محیط مجازی فعال نیست | پکیج‌ها را در محیط فعال نصب کنید |
| `AttributeError: module 'cv2' has no attribute 'face'` | نسخه‌ی `opencv-python` نصب است نه `contrib` | `pip uninstall opencv-python` و `pip install opencv-contrib-python` |
| `can't be opened` برای `trainer/model.xml` | هنوز کسی ثبت‌نام نشده / از پوشه‌ی اشتباه اجرا شده | با `server.py` یک نفر ثبت‌نام کنید، در پوشه‌ی درست اجرا کنید |
| `FileNotFoundError: ... haarcascade` | از پوشه‌ی اشتباه اجرا شده (`assets` پیدا نمی‌شود) | از داخل `faceDetectionWithCamera` اجرا کنید |
| `Access denied for user 'root'` | رمز MySQL فرق دارد | رمز را در هر دو فایل اصلاح کنید |
| `Can't connect to MySQL server` | MySQL روشن نیست | سرویس MySQL را راه بیندازید |
| `Connection refused` روی Redis | Redis روشن نیست | Redis را اجرا کنید، `redis-cli ping` باید `PONG` بدهد |
| پنجره‌ی دوربین باز نمی‌شود، `error: (-2:Unspecified error) ... backend` | OpenCV نسخه‌ی headless است یا کتابخانه‌های GUI ویندوز نیست | `opencv-contrib-python` معمولی نصب کنید (نه `...-headless`) |
| فریم سیاه به‌جای دوربین | دوربین وصل نیست یا `source` اشتباه است | ایندکس/آدرس RTSP را چک کنید |
| هیچ صورتی تشخیص داده نمی‌شود | نور کم، فاصله زیاد، زوم اشتباه | `zoom_factor`، نور، آستانه‌ها را تنظیم کنید |
| صورت تشخیص داده می‌شود ولی نام نمی‌آید / همیشه «نامشخص» | کد ملی به‌شکل متفاوت (مثلاً با صفر ابتدایی) در `NewPerson` ذخیره شده | کد ملی را یکدست نگه دارید (نکته ۶ بخش ۱۳) |
| «چهره شناسایی نشد یا چهره ناقص است» هنگام ثبت‌نام | صورت یا ۲ چشم پیدا نشد | عکس واضح‌تر، روبه‌رو، بدون ماسک |
| بعد از ثبت‌نام جدید، فرد شناخته نمی‌شود | برنامه‌ی دوربین مدل قدیمی را در حافظه دارد | برنامه‌ی دوربین را ری‌استارت کنید |
| `redis.exceptions.ResponseError` / `JSONDecodeError` در آموزش | کلید غیرمرتبط در Redis db=0 هست | `redis-cli -n 0 FLUSHDB` (فقط اگر داده‌ی دیگری ندارید) یا از db دیگری استفاده کنید |
| کلیک دوبار تمام‌صفحه اشتباه باز می‌کند | فرض ۱۰ پیکسل فاصله بین خانه‌ها با چیدمان واقعی نمی‌خورد | نزدیک‌تر به گوشه‌ی چپ-بالای تصویر کلیک کنید، یا `+10` را در خط ۲۰۰/۲۰۱ صفر کنید |
| سرور روی پورت ۵۰۰۰ بالا نمی‌آید | پورت اشغال است | پورت دیگر بدهید و آدرس کلاینت را عوض کنید |

## ۱۵. امنیت

این پروژه در حالت فعلی برای **شبکه‌ی محلی/تست** مناسب است و چند نکته‌ی امنیتی مهم دارد:

1. **رمز MySQL (`1234`) و نام کاربری `root` داخل کد hard-code شده است.** برای استفاده‌ی واقعی یک کاربر MySQL با حداقل دسترسی بسازید و رمز را از متغیر محیطی (`os.environ`) بخوانید.
2. **رمز دوربین RTSP داخل کد است** (`admin:shn123456789`) و داخل گیت‌هاب عمومی هم هست. اگر دوربین واقعی شماست، حتماً رمزش را عوض کنید و آدرس را عمومی نکنید.
3. **سرور هیچ احراز هویتی ندارد.** هر کسی که به پورت ۵۰۰۰ دسترسی داشته باشد می‌تواند افراد را اضافه/تغییر دهد. آن را فقط روی `localhost` یا شبکه‌ی مورد اعتماد باز بگذارید و پشت reverse proxy با احراز هویت قرار دهید.
4. **عکس چهره داده‌ی بیومتریک است.** محافظت از دیتابیس و پشتیبان‌گیری‌ها، رمزگذاری در حال ذخیره/انتقال و رضایت افراد لازم است.
5. **`debug=True` را در تولید خاموش کنید** — دیباگر Flask می‌تواند کد اجرا کند.

## ۱۶. ایده‌هایی برای توسعه

این‌ها انتظار پروژه نیستند، فقط مسیرهای طبیعی بعدی‌اند:

- ذخیره‌ی چند عکس برای هر نفر (چند زاویه/نور) برای دقت بیشتر؛ مدل باید چند نمونه از یک برچسب را بپذیرد.
- افزودن ستون `DATETIME` برای مرتب‌سازی و گزارش‌گیری راحت‌تر.
- یک مسیر `/train` جدا برای آموزش دستی بدون نیاز به ثبت‌نام جدید.
- استفاده از `labels_to_name.json` در برنامه‌ی دوربین برای نمایش نام بدون کوئری MySQL.
- پشتیبانی از بیش از ۴ دوربین و اندازه‌ی گرید پویا.
- جایگزینی LBPH با یک مدل مدرن‌تر (مثلاً یک مدل embedding) در صورت نیاز به دقت بالاتر.
